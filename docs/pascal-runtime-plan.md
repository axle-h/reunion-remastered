# Plan: retire the Borland Pascal run time

Status: **not started** (written 2026-10-12, from a survey of the code at
`edd28cf`). Stages 1-4 are ready to start. No open questions.
Decisions are dated where they are recorded.

## Background

The port began as a faithful copy of the DOS program, real-mode memory and
all, and then moved to native C memory: `mem[]`, far pointers, the
emulated Borland heap and EMS are gone (docs/port.md, "Memory"). That
work's plan, `docs/native-memory-plan.md`, is finished; it is in git
history up to the commit that deleted it.

What is left from Borland Pascal is its **run-time library and data
model**, still used throughout the game code:

| What | Where | Size (2026-10-12) |
|---|---|---|
| Pascal strings: `PString`, `PStrN`, `PSTR("...")`, `System_StrLoad/StrStore/StrConcat/Copy/CharToStr/Delete/StrLong/ValLong`, the per-file `ps()` helpers, and length-prefixed `const uint8_t *` parameters | 41 files | about 1,500 uses |
| The 6-byte `Real48` and its software arithmetic | `sim.c`, `vec3d.c`, `system.c` | about 30 call sites |
| Borland heap calls: `System_GetMem(size)` / `System_FreeMem(p, size)` | 27 files | 118 / 124 calls |
| Whole-64 KB-segment buffers (`System_GetSegment`) | 10 files | 19 sites |
| `ExitProc` chain, `ErrorAddr`/`ExitCode`, `Halt`, `RunError` | `gfx.c`, `system.c`, 12 files for `RunError` | 3 / 6 / 5 / 15 |
| Unit Ems: blocks that are always plain heap copies now | `ems.{h,c}` and 5 callers | 19 uses |
| `#pragma pack(1)` `DSeg`, little-endian only | `dseg.h` (generated) | one struct, 1,554 lines |

Recount the strings (the biggest item) with:

```sh
P='PSTR\(|PString|PStr[0-9]+|System_(StrLoad|StrStore|StrConcat|Copy|CharToStr|Delete|StrLong|ValLong)\b|\bps\('
for f in $(grep -rlE "$P" src); do echo "$(grep -oE "$P" $f | wc -l) $f"; done | sort -rn
```

Densest: `sim.c` (193), `planetinfo.c` (156), `intel.c` (151),
`surface.c` (111), `shop.c` (85), `pub.c` (76), `advisor.c` (67).

## Goal

Game code reads like ordinary C: NUL-terminated strings and `snprintf`,
`double` or integer maths, `malloc`-style allocation without sizes on
free, buffers sized to what they hold, and exits without a Pascal
`ExitProc` chain. Borland types stay only where they are **game data**:
the string fields of `DSeg` and its records (saved, hashed, and the
initial data in `src/game/dsinit.c`).

## What must not change

- **Behaviour.** The game plays exactly as now, fixes on or off. Random
  sequences, rounding and truncation must match the original.
- **The save format** (`docs/formats/save.md`). Original DOS saves still
  load.
- **The goldens** (`tests/golden/`, `tests/test_golden.c`): every case
  matches after every step. A mismatch is a bug in the change until proven
  otherwise.
- **The playthrough proof**: `test_play_game` still wins.

## Rules for the work

- **Don't regenerate goldens to make a step pass.** The one exception:
  removing a DS field, or changing what `state_serialize` hashes, changes
  the state stream even when behaviour doesn't. Then work in two steps:
  (1) only change what is hashed (e.g. add the field to `layout_fields` in
  `src/game/state.c`) with no other code change, and regenerate the goldens
  (`GOLDEN_WRITE=1`) from that code; (2) make the real change, and the
  goldens must match. Say so in the commit message. The native-memory work
  re-baselined twice this way.
- `src/game/dseg.h`, `dsfields.c` and `dsinit.c` are generated by
  `tools/gen_dseg.py` from `ghidra/symbols.txt` and `ghidra/types.pas`.
  Change DS types and fields there and regenerate. Don't edit the output
  by hand.
- Keep the Ghidra address comments (`// 405f:1a62`) on routines and the
  original's DS offsets in the field table. They are the link to the
  disassembly.
- Match the surrounding code's style (C23, `nullptr`, `enum : type`,
  comments explaining the original's behaviour). See `docs/port.md`.
- Playthrough fixture rules still apply (memory
  `playthrough-fixture-rules`): visible information only, clicks and keys
  only, saves through the API are fine, no date luck.
- Git is read-only unless Alex asks. When he does, commit directly on
  `main`, one commit per coherent step. Check `git status` first:
  uncommitted work in the tree is Alex's, so ask before touching it.

## How to check a step

```sh
cmake --preset debug && cmake --build --preset debug
ctest --test-dir build/debug                    # unit tests and goldens, no proof
cmake --preset release && cmake --build --preset release
ctest --test-dir build/release                  # adds golden_proof* and test_play_game (~2 min)
cmake --preset asan && cmake --build --preset asan
ctest --test-dir build/asan -R 'golden_|<touched tests>'
```

The tests need the game data in `vendor/Reunion_DOS_EN` (exit 77 = skipped
without it). If a golden fails, `test_golden` names the first differing
frame. Run it again with `GOLDEN_DUMP=FRAME GOLDEN_DUMP_DIR=DIR` from both
builds, then `test_golden compare A.state B.state` names the field (usage
at the top of `tests/test_golden.c`).

Every stage ends with all of the above green, and `docs/port.md` updated
where it describes what changed (its data-segment bullets on strings and
`real`, its "Memory" section on the heap).

## Stages

Stages 1-3 are independent; do them in this order (smallest first). Do
Stage 4.1 (the measurement) before any of them: it changes no code, and the
byte-buffer word accesses it finds overlap Stage 2.2's segment buffers. Each
numbered step should be small enough to review on its own.

### Stage 1: drop `Real48`

Only two places use it, and both have a small input domain.

1. **Cosine table** (`Vec3D_InitCosTable`, `src/game/vec3d.c`):
   `cos500[i] = Round(Cos(i * pi / 180) * 500)` for `i` = 0..360. Write a
   test that compares `lround(cos(i * pi / 180) * 500)` (with a local `pi`; `M_PI` is not standard C) with the Real48
   result for all 361 entries. If they all match, use the `double` form. If
   any differ, use a `static const` table of the Real48 results with a
   comment, not the double form.
2. **Normals** (`Vec3D_PrepareObject`, called from `vecload.c:386`): Real
   centroid, dot-product sign test, `Sqrt` and `Round(n / k)`. Write a
   `double` version and compare it with the Real48 one:
   - on every model and slot of every `VECTORS/*.VEC` in the game data
     (all outputs: normals and anything else the routine writes);
   - on a few million random int16 inputs, to see how often the two
     differ.
   Switch only if every game model matches. Note any differences on random
   inputs in a comment. If a game model differs, keep that computation
   bit-exact: do it in integers where possible, or keep a minimal Real48
   helper local to `vec3d.c`.
3. **Taxes** (`sim.c`, around line 570):
   `Round(Population * TechLevel * Resistance * (Attitude + 40) / 200000)`.
   Every operand is an integer, so the exact form is `int64_t` arithmetic
   with half-away-from-zero rounding. First bound each operand from the
   code (`TechLevel` is read as `int8_t`, `Resistance` ≤ 60, population
   capped by `maxPop`), then check that the Real48 chain is exact over that
   range: the significand is 40 bits, and the division truncates with a
   guard byte. Compare it with the `int64_t` form on all edge cases plus a
   random sweep. Switch only if they are identical.
4. Delete the Real48 routines from `system.{h,c}` and their tests in
   `tests/test_system.c`, keeping `real48_to_double` if `gen_dseg.py` or a
   test still needs it. `gen_dseg.py` always emits the `Real48` typedef; no
   DS field uses it (`grep Real48 src/game/dseg.h`). Leave the typedef if
   removing it complicates the generator.

### Stage 2: heap, segments, exits, Ems

1. **Allocation without sizes.** Replace `System_GetMem(size)` /
   `System_FreeMem(p, size)` with `game_alloc(size)` / `game_free(p)` (name
   to taste, in `system.c` or a new `game/heap.{h,c}`).
   - Keep what the current heap does: blocks are **zeroed**, and **tracked**
     so the next `system_init` frees them all. Restart and quit `longjmp`
     out of deep screen code (`src/main.c`) and abandon whatever the stack
     held, so a plain `malloc`/`free` would leak across restarts. Keep
     `system_heap_used` for the tests' leak checks (store each block's size
     in a header).
   - **Before converting, check every free against its allocation**: a
     `FreeMem` whose size differs from the matching `GetMem` is a partial
     free in Borland. Note how each is handled. `main_program.c` has 48
     `FreeMem` calls; start the audit there.
   - Keep the original's run-time errors where game code could trigger them
     (204: `FreeMem(nil)`), or prove they can't happen and assert instead.
2. **Segment buffers.** Each of the 19 `System_GetSegment` sites has a
   comment with the original's size (`// GetMem(0x1518)`). For each one,
   decide whether a 16-bit offset can actually wrap or run past that size:
   - if it can (e.g. the map layers in `surface.c:31`, where x or y 0 is
     below the layer), keep a 64 KB block and say why at the allocation;
   - if it can't, allocate the original's size and replace the `(uint16_t)`
     offset arithmetic with ordinary indexing, asserting the bound.
   `vec3d.c`'s `rdw`/`wrw` (word reads at byte offsets in a buffer) belong
   here too: make them typed `int16_t` arrays if the buffer's layout allows.
   Run ASan after each one: overruns that the 64 KB block hid become
   visible. Decide each one as in docs/bugs.md (reproduce deliberately with
   a comment, or fix behind `fixes`).
   **Keep** the flight view's backdrop and star table as they are
   (`shipmove.c`, ~line 582). Stars drawn past the backdrop land in the star
   table and change the random numbers. This is deliberate.
3. **Exits.** The only `ExitProc` is `Gfx_ExitHandler` (`gfx.c:1024`,
   installed at `gfx.c:1092`). Replace the chain with a direct call from
   the Halt/RunError path (a single hook in `system.c` if the layering
   needs it). Keep `system_exit_handler` and `system_runerror_handler`:
   `main.c` and the tests use them. `System_ExitProc` and
   `Gfx_SavedExitProc` are pointer fields, so the state stream already
   skips them. `System_ExitCode` is hashed; removing it from DS needs the
   two-step rule.
   **Fatal errors** (decided by Alex, 2026-10-12): report them through
   stderr and `SDL_ShowSimpleMessageBox`, not the original's error screen
   (`Gfx_ExitHandler` fades out, switches to text mode, prints "External
   or internal error! ... Error address" and waits for a key). Say what
   failed and where in port terms: the routine and, for file errors, the
   path. A 16-bit error address means nothing now. Then exit through
   `system_exit_handler` as today. Show the box only in interactive runs:
   headless runs (autopilot, `--replay`, tests, the offscreen video driver)
   write to stderr only, so a failure can never block on a dialog. Keep the 15 `RunError` call sites as
   fatal errors with their codes (2 file not found, 200 division by zero,
   ...); tests still catch them through `system_runerror_handler`.
   **No "not enough memory" error:** the port doesn't emulate the DOS
   memory limit, so `Gfx_ExitHandler`'s 203 branch ("Please run REUNION
   with more conventional memory or EMS") goes, and so does the heap's
   `RunError(203)` (`system.c:288`). If the C allocator itself fails,
   report that as a plain fatal "out of memory".
4. **Ems.** `ems.c` only allocates and frees now. Fold it into its callers
   (`main_program.c`, `gfx.c`, `gfxpath.c`, `title.c`). Keep the
   `TEmsBlock` DS fields unless the two-step rule is worth it: their
   bookkeeping is already excluded from the stream, and their contents are
   hashed through `state.c`. Update `state.c` if it reaches the blocks
   through `Ems_*`.

### Stage 3: C strings

Three layers: **interfaces** (functions taking strings), **game code**
(building and passing strings), and **game data** (strings in DS and its
records, which stay Pascal strings).

**Facts to rely on.**
- The game's text has no NUL bytes. All 1,802 lines of `TEXT\*` and the
  `.RAW` tables (decoded with `tools/text.py`) were checked on 2026-10-12;
  the only file that has them is `REUN_CD.TXT`, the CD's plain readme,
  which the game doesn't read. Re-check if another language's data is
  added. Bytes ≥ 0x80 do occur (glyph codes), so index fonts with
  `(uint8_t)` casts.
- File names are DOS paths (`"info\\info"`); `platform/fs.c` resolves `\`
  and case. Keep them as they are.

**Semantics to preserve.** Port each of these deliberately and test it:
- Truncation: `StrConcat` stops at 255 characters, and
  `StrStore(..., maxLen)` at `maxLen`. With `snprintf` into a buffer of
  `maxLen + 1` you get the same truncation; make sure each buffer is sized
  so.
- `Copy`/`Delete`: 1-based, clamping out-of-range index and count.
- `Str(value:width)` right-justifies with spaces (`%*ld`).
  `Val` reports the 1-based position of the first bad character.
- **Bytes past the length.** Several routines read or rely on them:
  `gfx.c:804-812` (pad with 52 spaces, then `Delete(s, width + 1, 255)`; a
  `BUG?` comment notes a read past the 256-byte buffer),
  `textfile.c:70` (`StrStore(…, 255)` into a 60-byte block),
  `textfile.c:202` (the reply code read past the end). Port each one
  deliberately.
- **Writes into game data.** When code stores into a DS or heap-record
  string (e.g. the message log's `string[50]` slots, `state.c:179`), the
  bytes written, including what is left past the new length, must be
  exactly as `StrStore` leaves them. They are hashed and saved.

**Steps.**
1. **Boundary helpers.** Add, next to the `PString` typedefs or in
   `system.h`:
   - `pstr_get(char *dst, size_t cap, const void *pstr)`;
   - `pstr_set(void *pstr, uint8_t maxLen, const char *src)`, which writes
     the same bytes `StrStore` does (length byte plus `len` characters; the
     tail untouched).

   Give them unit tests against the existing `System_Str*` before anything
   uses them. This is now the only way game code touches a `PStrN`.
2. **Leaf interfaces to `const char *`.** These are the headers that
   document Pascal-string parameters: `gfx.h` (`Gfx_DrawText*`,
   `Gfx_TypeText*`, `Gfx_DrawStatusText`, `Gfx_LoadPic*`, `Gfx_LoadFile`,
   `Gfx_OpenDataFile`, `Gfx_ShowGrafikaPic`), `sound.h`, `music.h`,
   `adlibmusic.h`, `textfile.h`, `message.h`, `mouse.h`, `intel.h`,
   `planetinfo.h` (`PlanetInfo_GetBody*Name`), `planetlist.h`. List them
   again with `grep -rli "pascal string" src --include=*.h`.
   - Do one interface at a time. Callers that still hold a `PString` convert
     at the call site with `pstr_get` into a local buffer. That keeps the
     tree compiling in a mixed state.
   - Functions that return a string through `PString *result` take
     `char *dst, size_t cap` instead.
   - The text editor (`TextFile_InputLine` and friends) edits a string in
     place; if that string is game data (a save name in DS), keep it a
     `PStrN` and convert at the editor's edges.
   - `gfx.c`'s own `str_long`/`out_write` go too.
3. **Game code, file by file**, least uses first (see the recount command
   above), ending with `sim.c`, `planetinfo.c` and `intel.c`:
   - `PSTR(...)` becomes a string literal; `StrLoad`/`StrConcat`/`StrLong`
     chains become one `snprintf`;
   - `PString` locals become `char[256]` (or the size the code needs);
   - the file's `ps()` helper goes.
   One file per step, with goldens green after each one. The `PSTR`
   compound-literal scope trap (docs/port-bugs.md #32) goes with it.
4. **Delete** `PSTR`, the unused `System_Str*`/`Copy`/`Delete`/`ValLong`
   and their tests. `PString` and the `PStrN` typedefs stay: DS fields use
   them (`Gfx_HeroCharset`, `Gfx_CharsetChars`, the name tables, record
   `Name`/`Caption` fields).
5. **Docs.** Update the strings bullet in `docs/port.md` ("The data segment")
   and the header comments that say "name is a Pascal string".

DS string fields that are really temporaries (`Pub_PersonStr`,
`AlienTalk_RaceStr`, `Main_SceneTrack`, `Shop_OreHeader`/`Shop_OreLines`)
stay in DS as Pascal strings (decided by Alex, 2026-10-12). Converting them
was worth a golden re-baseline only if it removed Pascal strings
altogether, and it can't: the strings in saved game data have to stay. The
group, building and message-log records are saved as they are in memory,
and `StrStore` leaves the bytes past a string's new length untouched. So
saves carry those stale tail bytes, and only an in-memory Pascal string
keeps them for a byte-identical round trip (the `load_*` goldens check
it). If saves ever stop needing to be byte-identical, revisit this.

### Stage 4: misaligned accesses

`DSeg` and its records are packed (`#pragma pack(1)`): the original's
globals back to back, so many 16- and 32-bit fields sit at odd addresses.
Reading `ds.Field` directly is fine, because the compiler knows the member is
packed and emits safe code. The undefined behaviour comes from reaching such
a field through an ordinary typed pointer: `int16_t *p = &ds.X`, a cast
like `(PString *)&ds.Y` or `*(int16_t *)(buf + off)` on a byte buffer.
x86-64 and ARM64 tolerate these accesses. Other targets may fault or be slow,
and the optimiser may assume the access is aligned. The `asan` and `trap`
presets have passed `-fno-sanitize=alignment` since the first port commit
(`49e72a1`), when everything lived in the emulated `mem[]` and misaligned
access was unavoidable. That reason is gone.

1. **Measure** (agreed by Alex, 2026-10-12; no code changes).
   - Configure a separate build directory with alignment checking on and
     recoverable, e.g.
     `cmake --preset debug -B build/align -DCMAKE_C_FLAGS="-fsanitize=alignment -fno-omit-frame-pointer"`
     and `cmake --build build/align`.
   - Run the unit tests, every golden case and the soak seeds from
     `tools/soak.sh` with `UBSAN_OPTIONS=print_stacktrace=1`. Then run
     `golden_proof` from a release-type build with the same flag.
   - Collect the `misaligned address` reports and dedupe them by source
     line. UBSan already reports each source location once per process.
   - Sort them by cause:
     - (a) pointer to a packed DS or record member;
     - (b) word or longword cast on a byte buffer (heap blocks, file data,
       `rdw`/`wrw`);
     - (c) anything else.
   - Add a static view as well: count the `-Waddress-of-packed-member` and
     `-Wcast-align=strict` warnings, and note any that the runtime pass
     didn't hit.
   - Report the counts, the per-file breakdown and a few typical sites to
     Alex. Record the numbers here.
2. **Fix the misaligned accesses** (agreed by Alex, 2026-10-12: all of
   them, in the order step 1's breakdown suggests). This doesn't need
   `DSeg` unpacked.
   - (a) becomes direct `ds.X` access, or a pointer to the packed struct
     itself: a pointer to a packed record type is fine.
   - (b) goes through `memcpy`-based little-endian accessors (`rd16le`,
     `wr16le`, ...) or a properly typed, aligned buffer.
   - Goldens must match; they shouldn't change at all.
   - Then remove `-fno-sanitize=alignment` from the presets, so new
     misaligned accesses fail the `asan` and `trap` runs.

## Out of scope

- **The game drives its own loop.** Screens wait on the retrace in their
  own loops, pump events from inside the waits (`timing_wait_retrace`,
  `Crt_ReadKey`), and leave by `longjmp` to `main()`. Inverting that into
  an event-driven frame callback means rewriting every screen. If a web
  build is ever wanted, Emscripten's ASYNCIFY (or running the game on its
  own thread or coroutine) is far cheaper. `crt.{h,c}` stays with it.
- **16-bit integer types and wraparound** in game logic: behaviour depends
  on them.
- **DOS paths** in file names (see Stage 3).
- **Big-endian hosts and an unpacked `DSeg`** (decided by Alex,
  2026-10-12: not wanted). The hosts that would gain are all niche:
  AmigaOS 4 / MorphOS and old PowerPC Macs, Wii-family homebrew, s390x,
  big-endian POWER and SPARC. Every realistic target is little-endian:
  Windows, macOS and Linux on x86-64 or ARM64, and WebAssembly. So
  `dseg.h:8`'s little-endian `#error` stays, and `DSeg` stays packed: the
  original reads and writes past arrays into the next globals
  (docs/port.md, "The data segment"). Stage 4 makes the packed layout
  safe instead.
